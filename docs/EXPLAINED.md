# 从零讲清楚：这个项目做了什么、每一块是什么意思

写给机器学习基础薄弱的读者。每一块先说"它是什么"，再说"我做了什么"，最后说"和 B 站方案的差别在哪、为什么"。

---

## 先看一眼全貌

那个 B 站视频（VoxEMW）是六块积木串成的一条流水线：

```
你的麦克风
   │
   ▼
① 判停       ─ 你说完了没？                （Silero VAD + SmartTurn）
   │
   ▼
② 转文字     ─ 你说了什么？                （Qwen3-ASR）
   │
   ▼
③ 大脑       ─ 他会怎么回？                （DeepSeek / 本地大模型）+ ⑤ 人设
   │
   ▼
④ 合成语音   ─ 用他的嗓子念出来            （VoxCPM2 / Qwen3-TTS）
   │
   ▼
⑥ 数字人     ─ 嘴型跟着声音动的画面        （SoulX-FlashHead）
   │
   ▼
你的浏览器
```

**核心事实：①②③④⑤ 已经全部在你的 Mac 上跑起来了，而且实测比 B 站视频还快。⑥ 是全部问题所在。**

你现在在网页上看到的"人"，是两段录像在循环播放，嘴型不是算出来的。那是我放的占位符，为了让布局和状态切换先能工作。它不是数字人。这一点我之前没说清楚，是我的问题。

## ① 判停：Silero VAD + SmartTurn

**它是什么。** VAD 是 Voice Activity Detection，"语音活动检测"。一个 2MB 的小模型，跑在 CPU 上，每 32 毫秒看一眼麦克风，输出一个 0 到 1 的数：现在有没有人在说话。它只管"有没有声音"，不管说的是什么。

光有 VAD 不够。你说话中间停顿思考半秒，VAD 会以为你说完了，他就抢话。所以 VoxEMW 又加了 SmartTurn：一个听"语调"的模型，看最后几秒的音调走向，判断是"句子结束"还是"还没说完"。

**我做了什么。** `voxck/vad.py`。两个模型都接上了，另外加了三个实战里必须有的细节：
- 前置缓冲 320ms：VAD 反应需要时间，不留缓冲会吃掉你每句话的第一个音节。
- 尾音等待 350ms：你一停顿就判停太急。
- 兜底 900ms：SmartTurn 拿不准时最多再等 0.9 秒，否则它可能一直等下去。

**状态：完成。** 纯 CPU，不占 GPU。

---

## ② 转文字：Qwen3-ASR-1.7B

**它是什么。** ASR 是 Automatic Speech Recognition，"语音识别"。音频进，文字出。和 B 站视频用的是同一个模型。

"1.7B" 是 17 亿参数。参数可以理解为模型"脑子里的旋钮"数量，越多越准，也越慢。

**我做了什么。** `voxck/asr.py`。用 MLX 跑（MLX 是苹果为 Mac 芯片做的模型运行框架，相当于 Mac 上的 CUDA）。加了热词 "feminism"，避免听成别的词。

**实测：** 一句话 180 到 300 毫秒出文字。**状态：完成，与 B 站方案相同。**

---

## ③ 大脑：DeepSeek v4 → 本地 Qwen3-30B-A3B

**它是什么。** 就是 ChatGPT 那类大语言模型。它读到两样东西：你刚说的话，加上 ⑤ 那份人设说明书，然后写出他会说的回答。

**为什么换了。** 你最初的要求是"代码和模型都跑在本地 MacBook 上"。DeepSeek v4 只能通过 API 调用，也就是把你的话发到他们的服务器，模型权重不公开，无法本地跑。所以换成了本地能跑的 Qwen3-30B-A3B。

**30B-A3B 是什么意思。** 总共 300 亿参数，但每次只激活 30 亿。这叫 MoE（Mixture of Experts，专家混合）：模型内部分成很多个"专家"，每个词只找其中几个来算。效果是"有 300 亿的知识量，30 亿的速度"。这是它能在 Mac 上跑得够快的原因。

**我做了什么。** `voxck/llm.py`，加上 `run.py` 里起的本地推理服务。关键处理：
- 关掉"思考模式"：Qwen3 默认会先自言自语推理几秒再回答，辩论场景等不起。
- 前缀缓存：人设说明书有 4000 多个词，每一轮都要重读。缓存后只算一次，之后复用。实测命中率 99.7%。
- 每轮最多 140 个 token，回答被截断时丢掉不完整的尾句。

**实测：** 从收到你的文字到吐出第一个字约 740 毫秒。**状态：完成。**

**如果你想换回 DeepSeek。** 我们的代码用的是 OpenAI 兼容协议，DeepSeek API 也是。改一行配置就能切换。代价是不再本地、对话内容会发到对方服务器。收益是英文论辩质量可能更好。

## ④ 合成语音：VoxCPM2 → Qwen3-TTS

**它是什么。** TTS 是 Text To Speech，文字转语音。"音色迁移"或"克隆"的意思是：给模型一段 8 秒他本人说话的录音，加上这 8 秒说的文字，之后它就能用他的嗓子念任何新句子。不需要训练，这叫零样本克隆。

**为什么换了。** VoxCPM2 是 B 站方案用的。它的 Mac 移植版有一个致命问题：不支持流式输出。整句话合成完才给你，一句话要等 3 到 11 秒才听到第一个音。Qwen3-TTS 是一小块一小块吐出来的，300 毫秒左右就开口。另外它的英文错误率也更低（1.24 对 1.84）。

**我做了什么。** `voxck/tts.py`。
- 参考音在 `assets/ck/ref.wav`，8 秒，从一期播客切的。选播客而不选集会视频是有原因的：克隆会把韵律一起复制，拿他对着人群喊的片段，克隆出来说什么都像在吼。几个候选你听过，选了 A。
- 打断机制：你一开口，正在合成的音频立刻作废。
- 句子攒够 12 个词再合成一块，太短的块音质会崩。

**实测：** 从你说完到听见他开口，1.1 到 1.4 秒。B 站视频作者自报是 2 到 2.5 秒。**状态：完成。**

## ⑤ 人设：女娲 nuwa-skill 的思路 → 我们自己的 Ledger 方案

**它是什么。** "蒸馏人设"听起来像训练，其实不是。它是写一份很长的说明书，放在大脑每次读的开头：他是谁、他的立场、他怎么说话、他怎么应对反驳。大模型读完就"扮演"他。女娲 nuwa-skill 是一套写这种说明书的方法论。

**我做了什么。** `personas/ck-gender.md`，4000 多词，只覆盖你选的性别议题。结构：
- 26 条立场，每条附他本人的原话出处。规则是：立场只能从这 26 条里来，不许编。
- 13 种他常用的辩论打法。
- 他真实的让步方式：什么时候会退一步，退到哪里就不退了。
- 说话规则：第一句不超过 10 个词，全文不超过 90 个词，最多问一个问题。
- 不出戏：不说"我是 AI"，被问也含糊带过。

**踩过的坑，也是和女娲方案最大的区别。** 说明书里写的规则，模型有一定比例会不遵守。实际发生过：把说明书里的示例句原样背出来；把一句引用改成第二人称对着你说；连续几轮说一样的开头。每次我加一条禁令，它换个方式再犯。

结论是：**描述性的东西写在说明书里，硬性约束必须写在代码里。** 所以加了 4 层代码守卫（`voxck/guard.py`、`voxck/semantic_guard.py`）：
1. 正则：拦截对你本人下的人生判决句式。
2. 复读检测：和前几轮重合度过高的句子直接丢。
3. 词数预算：超 90 词硬切。
4. 语义裁判（TypeSafe）：一个外部小模型判断这句话有没有编造事实、有没有对你个人下结论。

验证集 10 条全部拦住。**状态：完成。**

## ⑥ 数字人：SoulX-FlashHead

**它是什么。** 输入他的一段短视频加上 ④ 合成的音频，输出一段新视频：他的脸还是原视频的脸，但嘴型按音频重新画。B 站视频里那个看着你、嘴跟着声音动的效果，就是这一块。

VoxEMW 用的是 SoulX-FlashHead，一个 13 亿参数的视频扩散模型。"扩散"意味着每一帧要反复去噪好多轮才画出来，计算量很大。作者在 RTX 4090 上跑到 3.5 倍实时。

**问题在哪。** 一句话：你的 Mac 没有 4090。

我实测了你这台机器的算力：bf16 精度 20 TFLOPS。4090 是 165。差 8 倍。按这个比例，SoulX 在你机器上大约每秒画 11 帧，视频需要 25 帧。这不是调参能解决的，是算力墙。

**我试了三条路。**

第一条，MuseTalk。一个更老更轻的口型模型，有 Mac 移植版。原理不同：不是多轮扩散，而是一步"修补"，把嘴部区域按音频重画一次。我用它做出了一段真正口型同步的视频（你打开过的 `lipsync_demo.mp4`，嘴型是算出来的）。但端到端只有每秒 4.5 帧。而且它和 TTS 抢同一块 GPU，一起跑时声音会断。

第二条，神经引擎。你的 Mac 里有第三块芯片 ANE（Apple Neural Engine），GPU 再忙它也不受影响。我用一个只画嘴的小网络在上面实测：每帧 1.49 毫秒，GPU 打满时也一样。够快 14 倍。代价是这个小网络没有现成权重，必须拿他本人 3 到 5 分钟坐着正对镜头的视频来训练。你给的三段视频我逐帧扫过：街头那段他侧对且 60% 是 Vivek，58 分钟合辑镜头对着提问者，竖版 shorts 字幕烧在画面里。没有一段能用。

第三条，昨晚刚写的 `voxck/face.py`。回头看 MuseTalk 的 4.5 帧，我发现一半的计算其实不依赖音频（人脸检测、裁剪、编码底子帧），可以提前算好存着。运行时只算依赖音频的那一半。今天实测：**15 帧每秒**，GPU 空闲时。拆开看，画嘴的网络 40 毫秒一帧，把结果解码成图片又 38 毫秒一帧，两头各占一半。之前记录的 30.7 帧是微基准被 MLX 惰性求值骗了，已在 `docs/musetalk-measured.md` 里修正。

15 帧的意思：离 25 帧差 40%。有两个已知的补救办法，但都不能让它稳过 25：换轻量解码器最多到 24 帧；或者按 12.5 帧渲染、每帧播两次，画面会略"卡"，但能实时。

**状态：未完成。这是全部问题所在。**

- ⑥ 上花了大量时间做算力实测、三条路的可行性验证、素材扫描。结论都是"不行"或"要素材"。也看不见。

所以"几周没进展"从你的角度是成立的。

## 现在的两条路

**A. 租一张 4090。** 把 VoxEMW 原样跑起来，SoulX 直接可用。我们的大脑、音色、人设全部复用。最快能看到 B 站视频那个效果。代价：不本地，按小时计费，要架隧道把音视频流传到你浏览器。

**B. 坚持本地。** 两个子选项：
- B1：MuseTalk 按 12.5 帧渲染接进去。前提是大脑不在本地 GPU 上（你的 DeepSeek 正好解决这个）。效果是他真实影像加算出来的嘴，嘴部动作略卡，开口约 2.5 到 3 秒。这是本地最快能看见东西的路。
- B2：ANE 训练路线。需要你先找到 3 到 5 分钟他坐着正对镜头的素材，之后 3 到 5 个工作日。效果比 B1 快，比 SoulX 糙。

这两件事不互相排斥。
